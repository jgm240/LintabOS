# LintabOS 0.3.8 (pre-release)

Broadens the 0.3.6 partition picker, and gives a definitive way to check for the actual cause behind it.

## The change

`list_ntfs_partitions()` matched by *probed filesystem content* (`fstype == "ntfs"`), which misses a real Windows
partition whenever that content probe doesn't come back clean. Renamed to `list_microsoft_data_partitions()` and
matched by *GPT partition type* instead — the same Microsoft-data GUID `windows_partitions()` already uses — which
doesn't depend on content probing at all. The EFI partition, LintabOS's own root, and swap can never appear here:
they carry different GPT types, by construction.

The mount itself is now filesystem-aware too: previously hardcoded to the `ntfs3` driver regardless of what's
actually there, it now uses `exfat` for an exFAT volume and keeps `ntfs3` as the default otherwise. BitLocker is
still excluded, and that exclusion doesn't depend on the content probe either — `is_bitlocker()` reads the real boot
sector directly.

## A reported "File system (null) not configured in kernel" when opening an NTFS partition in Files

This is a different code path (GNOME Files' own on-demand mounting via udisks2, not anything LintabOS controls) and
points at the same underlying question this release is about: blkid/lsblk couldn't determine the partition's
filesystem type at all. One real possibility is BitLocker — an encrypted volume has no readable NTFS signature for a
content probe to find, which would also explain why automatic detection never found "the Windows install" in the
first place. `is_bitlocker()` checks the real boot sector directly rather than trusting that same confused probe, so
it's the way to get a definite answer.

## What was checked

All 20 loop-device tests still pass, including a real NTFS mount with the new fstype-aware fstab line. A new unit
test proves a partition with a blank/unrecognised probed fstype is now found (and the EFI partition, by GPT type,
still isn't).
